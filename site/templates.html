lead-routing · 客户线索分发

表单来一条线索，去重后写进 CRM，同时通知销售群

Webhook 触发 · 外部调用失败自动重试 3 次 · 同一条线索永不被处理两次

触发
POST /webhook/lead-routing，body 含 email、company、source
需要的凭证
Postgres（自带）、Slack Bot Token、CRM 接口地址
失败时会发生什么
CRM 或 Slack 失败 → 重试 3 次 → 仍失败则写一行到 workflow_errors，不会静默丢数据
去重粒度
email::source。想「同一个人不同渠道只收一次」，把 source 从 key 里去掉即可

support-triage · 工单分类路由

工单进来，LLM 判断类别与优先级，自动发到对应频道

Webhook 触发 · 模型返回坏 JSON 也不卡死 · 同一工单只处理一次

触发
POST /webhook/support-triage，body 含 ticketId、text
需要的凭证
Postgres（自带）、DeepSeek、Slack Bot Token（频道 support-billing 等需先建好）
失败时会发生什么
LLM 调用失败 → 重试 3 次 → 落表；模型返回不合法 JSON 时不报错，兜底成 category=other 照常发出
输出
Slack 消息含：优先级、类别、一句话摘要、建议回复草稿

invoice-parsing · 发票结构化解析

发票 PDF 变结构化字段，够可信进财务系统，不够可信进人工队列

Webhook 触发（可换邮件）· 置信度低于 0.8 自动转人工 · 重复邮件不会重复入账

触发
POST /webhook/invoice-parsing；想用邮件触发，把第一个节点换成 IMAP / Gmail 即可，后面的链路不动
需要的凭证
Postgres（自带）、PDF 转文本服务、DeepSeek、财务系统接收接口
失败时会发生什么
PDF 读不出来 → 重试后落表（不进复核队列，因为人工也没东西看）；字段只抽出一半 → 不报错，直接进 review_queue 并写明缺哪几个字段
置信度怎么算
5 个核心字段的填充率。0.8 意味着只允许缺 1 个字段

rss-summary · RSS 摘要入库

每小时读一次 RSS，新文章摘要后写进 Notion

定时触发 · 按 guid 去重，读过的永不重复 · 摘要带「为什么重要」一行

触发
每小时
需要的凭证
Postgres（自带）、DeepSeek、Notion Token + 数据库 ID（属性：Name、Link）
失败时会发生什么
LLM 或 Notion 失败 → 重试 3 次 → 落表。注意：该文章的去重键已占用，需要人工从错误表重放（换来的是「不漏也不重」）
为什么 Notion 走 HTTP 而不是官方节点
官方节点属性映射跨版本改过几次，导入易出问题；直接打 /v1/pages 在任何版本行为一致

sheets-notion-sync · 表格到 Notion 同步

每 15 分钟扫一次表格，改动过的行才建 Notion 记录

定时触发 · 单向同步，Notion 的编辑不会被覆盖 · 按行号 + 更新时间去重

触发
每 15 分钟
需要的凭证
Google Sheets OAuth2、Postgres（自带）、Notion Token + 数据库 ID
失败时会发生什么
Notion 失败 → 重试 3 次 → 落表；下一轮会自动重试同一行，且不会产生重复页面
为什么只做单向
双向同步必须定义冲突规则，而任何自动规则都会在某一刻悄悄覆盖用户的修改。单向没有这个问题

daily-digest · 每日运营简报

每天早 9 点，把过去 24 小时的运行数字写成简报发出去

定时触发 · 一天只发一封 · 数字由 SQL 算好，模型只负责措辞

触发
每天 09:00（时区跟随 GENERIC_TIMEZONE）
需要的凭证
Postgres（自带）、DeepSeek、SMTP
失败时会发生什么
LLM 或 SMTP 失败 → 重试 3 次 → 落表，不发半份报告；当天去重键已占用，重发需手动删 key
为什么不让模型做算术
它会把 3 和 5 加起来说成 9 而不报错。数字一律由 SQL 算好传进去

三步导入

第一步 · 起环境

装好 Docker Desktop 并让它运行，然后双击 start.bat。首次会拉镜像（约 1.5 GB），之后秒起。

n8n 跑在 localhost:5678，Postgres 在 localhost:5433。端口刻意避开常用默认值，防止和你机器上已有的服务撞车。

第二步 · 导入 JSON

docker compose exec n8n n8n import:workflow --input=/data/templates/lead-routing/workflow.json

导入后工作流是未激活状态，这是正常的。

第三步 · 填凭证并激活

在 n8n 编辑器里打开模板，节点上会标红提示缺少凭证。建好凭证、逐个选中，点右上角 Publish（n8n 2.x 里「激活」按钮叫 Publish）。

建议先跑 daily-digest：它只依赖本机数据库和邮件，不需要接任何业务系统。跑通它，说明你的 LLM 与 SMTP 凭证都是对的，再去接其他模板会省掉一半排查时间。

三条工程契约

这 6 个模板不是各自为战，它们共享同一套约定。这也是它们和你从网上随便下的模板包的区别。

契约做法为什么必须这样
重试
retry		 外部调用节点开 retryOnFail，3 次、间隔 3 秒。写库节点不重试 第三方接口抖动是常态；写库重试会重复写入，靠数据库约束兜底而不是靠重试
错误分支
error branch		 节点设 onError: continueErrorOutput，错误输出统一接一个 Log Error 节点 失败必须留痕，不能静默。不用独立 Error Workflow，因为跨工作流引用在客户环境导入后会失效
幂等
idempotency		 processed_keys 三节点：Claim（租约式占位）→ Claimed?（闸门）→ Mark Done（成功落章） Code 节点里「先查再写」在并发和重试下有竞态；只靠 ON CONFLICT DO NOTHING 会让失败的 key 永久占死，且 0 行时链路并不会停

完整规范见仓库里的 templates/_shared/README.md，新增模板照抄即可。
