AutomationKit 系统设计文档

自托管 n8n 工作流模板包 · 6 个模板 · 共用一套重试 / 错误分支 / 幂等契约
版本 0.1.0 ｜ 2026-11-01 ｜ 目标运行时 n8n 2.45.0 + Postgres 17 ｜ 单团队自托管

设计目标与边界

它是什么

一套可直接导入 n8n 的工作流模板，客户用一条 start.bat 起好环境，导入 JSON、填凭证、点激活就能用。对应 Upwork Project Catalog 服务包（$95 / $190 / $380）。

解决的三个真实问题

客户痛点本项目的应对
买来的模板跑两天就静默失败，没人知道每个外部调用都带错误分支，失败写进 workflow_errors 表并保留原始 payload
重试造成重复写入（同一张发票入账两次）幂等键 + 数据库唯一约束，重试与并发下都不重复
模板锁死在某个 SaaS 平台里，导不出来全部是 n8n 原生 workflow JSON，可导出、可改、可迁走

明确不做的事

  • 不做自研 n8n 节点：客户环境装不了自定义节点，反而增加交付摩擦
  • 不做多租户：一个实例服务一个团队，租户隔离是另一个价格档位的事
  • 不做托管服务：只交付可自托管的东西，不承担代运维
  • 不内置 OCR：图像型发票依赖外部 PDF/OCR 服务，模板只负责编排

启动顺序与依赖

  1. start.ps1 检查 Docker 引擎是否在运行（不是检查 CLI 是否存在）
  2. 没有 .env 就生成一份，含 48 位十六进制的 n8n 加密密钥与 32 位数据库密码
  3. docker compose up -d
  4. Postgres 先起，健康检查通过后 n8n 才启动（depends_on: condition: service_healthy）
  5. Postgres 首次初始化时执行 sql/init.sql 建三张表
  6. 脚本轮询 ak-n8n 的 healthcheck 状态，最长 240 秒

为什么先查引擎再查 CLI：本机实测过 docker --version 能正常输出，但引擎未启动时 docker compose up 会报 failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine。所以脚本里判定依据是 docker info 的退出码，不是版本命令。

数据模型

三张表，全部由 sql/init.sql 在 Postgres 首次启动时创建。它们不承载业务数据，只承载可靠性。

processed_keys · 幂等键

字段类型作用
keytext PRIMARY KEY事件唯一标识。主键即唯一约束，重复插入必被拒
workflowtext NOT NULL哪个模板写的，便于排查
payloadjsonb原始事件快照，失败时可人工重放；占位节点的 RETURNING 会把它带回链路，闸门节点再还原成下游可读的字段
statustext NOT NULLclaimed = 本次运行已占位（10 分钟租约）；done = 已成功，永久去重
created_attimestamptz默认 now()，用于按时间窗口统计
updated_attimestamptz租约时间戳。失败遗留的行在 10 分钟后可被重新认领

为什么要 status 和租约（lease）：只有主键约束时，一次失败（LLM 超时、CRM 5xx）会把 key 永久占死，客户修好配置重投同一条事件也毫无反应。加上状态与租约后：成功 → done 永不再处理；失败 → 停在 claimed，10 分钟后自动可重试；并发重投 → 仍在租约内，直接被挡住。

各模板的 key 构造规则见 templates/_shared/README.md：线索用 email::source、发票用 messageId::attachmentName、RSS 用 guid、同步用 row_number::updated_at、日报用日期。

workflow_errors · 错误落表

所有模板共用一个叫 Log Error 的节点写入这张表。客户只需要在一个地方看全部失败。

review_queue · 人工复核队列

低置信度的结果不进业务表，先进这里。以发票为例：5 个核心字段只填出 3 个，confidence = 0.6 < 0.8，就写进队列并在 reason 里写明缺哪几个字段。

设计原则：业务表由客户自己定义，我们只交付可靠性基础设施。这样模板能套进任何业务领域，而不需要客户改我们的表结构。

工程契约

6 个模板共用三条规则。它们是同一套约定的 6 次实例化，不是 6 份独立稿子。

契约强制做法判定「做到」的标准
重试
retry		 外部调用节点 retryOnFail: true + maxTries: 3 + waitBetweenTries: 3000 断网后执行，节点执行记录里能看到 3 次尝试
错误分支
error branch		 onError: continueErrorOutput，error output 连到唯一的 Log Error 节点 故意让接口返回 500，workflow_errors 里多一行且带 message
幂等
idempotency		 三节点：Claim（INSERT ... ON CONFLICT DO UPDATE ... WHERE status <> 'done' AND updated_at < now() - 10min）→ Claimed?（Code 闸门）→ Mark Done（UPDATE ... SET status='done'） 同一请求连发两次，第二次在闸门处被过滤成空分支，业务侧只有一条记录

幂等的实现细节很关键（实测修正了两处错误认知）：

① 0 行不等于链路停止。n8n 2.45.0 的 Postgres 节点在 SQL 返回 0 行时，输出是一条 { "success": true }，不是空输出。所以必须显式加一个 Claimed? 闸门把没有 key 的 item 过滤掉，否则主链路会带着这条空数据继续往下跑，重复写入业务系统。

② ON CONFLICT DO NOTHING 会把失败的 key 永久占死。改成「claimed / done 两阶段 + 10 分钟租约」后，成功永不再发，失败可自愈重试，并发重投仍被挡住。

③ 占位节点会吞掉 payload。它的输出是 SQL 行，下游原本读 $json.email 之类字段的节点全部拿到 undefined。所以 RETURNING key, payload，由闸门节点把 payload 还原成下游可读的 item。

决策 D1 · 用 HTTP 节点调 LLM，不用 LangChain 节点

方案优点缺点
LangChain 节点
@n8n/n8n-nodes-langchain.*		 内置链式编排、记忆、向量库集成 版本迭代快、凭证类型多、依赖额外安装；客户环境版本不一致时最容易导入失败
采用 · HTTP Request 兼容所有 n8n 版本；换模型只改 URL 与 body；输出格式用 response_format 显式约束 需要自己拼请求体，比链式节点多写几行 JSON

拒绝理由：交付物要在未知版本的客户环境里可靠导入，兼容性优先级高于开发便利性。

决策 D2 · 节点级错误输出，而非独立 Error Workflow

方案优点缺点
独立 Error Workflow 集中处理、一处配置 靠 workflow ID 互相引用；导入客户环境后 ID 不匹配，直接失效且静默
采用 · 节点级 error output 自包含，导入即用；错误与失败节点在同一张图上，排查直观 每个模板都要多一个 Log Error 节点

拒绝理由：交付物不能依赖「导入后还需要人工重新连线」这种前提。生产环境可以再挂一层全局 Error Workflow 兜底，但模板本身必须自包含。

决策 D3 · 幂等落在数据库约束，不放在 Code 节点

方案行为结论
Code 节点先查再写两次并发执行可能都查到「不存在」，然后都写入❌ 有竞态（race condition）
采用 · 唯一约束 + ON CONFLICT原子操作，数据库保证只有一个成功✅ 唯一可靠做法
Redis 分布式锁可行，但引入额外组件❌ 增加部署复杂度，收益不抵

决策 D4 · Postgres 映射到 5433

宿主机已有大量服务占端口：3000 / 3001 / 3002 / 5173 / 5174 / 15555 / 15556 / 15600 / 15601 / 15610 / 15611。5432 虽然没有被占用，但它是最常见的本地 PG 默认端口，客户自己机器上很可能已经跑着一个 Postgres。

结论：容器内仍是 5432（n8n 用容器网络连它），只在宿主机侧映射成 5433。这样本地调试连得上，又不和客户的既有实例撞车。

决策 D5 · 首批只做 6 个模板

原方案 10–12 个。首批收敛到 6 个的理由：

  • 6 个跑通的模板 > 12 个没验证过的。模板的价值在「导入即用」，没实测过的 JSON 是负资产
  • 3 个 Webhook + 3 个定时的组合已覆盖三类客户：事件驱动、内容聚合、数据同步
  • 契约一旦固化，第二批 6 个只是复制节奏，不会引入新风险

第二批候选：会议录音转行动项、客服满意度回访、竞品价格监控、招聘简历初筛、周报自动生成、多平台库存同步。

风险与降级策略

风险影响当前应对
镜像 tag 2.45.0 不存在或拉取失败 客户起不来环境 tag 来自本地 n8n 源码 package.json 的 version 字段；拉取失败时降级为 n8nio/n8n:latest 并在 README 注明
Webhook 是明文 HTTP 凭证可能在传输中泄露 README 明确要求生产环境前置 Nginx / Caddy 做 TLS
rss-summary 先占位后调用 LLM 失败的文章不会自动重试 有意取舍：保证不漏也不重；失败项留在 workflow_errors 待人工重放，已在模板 README 写明
客户 n8n 版本与模板版本不一致 节点参数可能显示异常 只用内置节点、不用 LangChain 节点、不依赖自定义节点；全套 typeVersion 已对照 n8n 2.45.0 源码核对
凭证泄露风险 客户密钥外泄 模板内全部为占位符，.env 已进 .gitignore，仓库不含任何真实密钥

运维手册

日常命令

docker compose ps                      # 状态
docker compose logs -f ak-n8n          # 跟随日志
docker compose down                    # 停止，保留数据
docker compose down -v                 # 停止并清空数据（重建表结构）
docker compose exec postgres psql -U autokit -d autokit

排查失败的三条 SQL

-- 最近 24 小时的错误
select workflow, node, message, created_at
from workflow_errors
where created_at >= now() - interval '24 hours'
order by created_at desc;

-- 有没有重复处理（正常应返回 0 行）
select key, count(*) from processed_keys group by key having count(*) > 1;

-- 待人工复核的发票
select item_key, reason, created_at from review_queue order by created_at desc;

重新发送某天的日报

-- 方式一：直接删掉占位（下一次运行视为全新事件）
DELETE FROM processed_keys WHERE key = '2026-11-01';

-- 方式二：只让租约过期，保留 payload 与审计痕迹（推荐）
UPDATE processed_keys
SET status = 'claimed', updated_at = now() - interval '11 minutes'
WHERE key = '2026-11-01';

备份

两个 Docker volume：ak_n8n_data（工作流与凭证密文）与 ak_pg_data。凭证密文依赖 N8N_ENCRYPTION_KEY——备份时两者必须一起备份，只备份 volume 而丢了 key，凭证就再也解不开。

检查项状态说明
节点参数在 UI 中无红字部分验证CLI 执行会做一次 issue 扫描（Slack 频道占位符就是这样被发现并修掉的）；剩余节点仍需在编辑器逐个打开确认
真实第三方写入未验证Slack / Notion / SMTP / CRM 均为占位地址，验证的是「失败被正确捕获」，不是「写入成功」

结论：从「导入 → 激活 → HTTP 入口 → 业务处理 → 失败留痕」整条链路已实机走通，而且是在真跑过程中修掉了 4 个只有跑起来才会暴露的缺陷（0 行不停链路、失败 key 永久占死、payload 被占位节点吞掉、错误表节点名恒为 unknown），外加日报取数写错来源、Slack 频道占位符导致整条流被判 has issues 两个问题。仍未验证的是「真实第三方写入成功」，依赖客户自己的凭证与域名。

运维备忘（n8n 2.x 激活机制）：只有 workflow_entity.active = true 是不够的，2.x 还要求 activeVersionId 指向一个已发布版本，否则 Webhook 不注册、请求返回 404 The requested webhook is not registered。在编辑器里点开关时 n8n 会一并处理；用脚本或 SQL 直接改库时必须两个字段一起设，然后重启容器让 ActiveWorkflowManager 重新加载。

配套文档：本文只记录"设计成什么样"。至于"凭什么说它一直跑得对"，见 《可靠性保障》 —— 四层防线（L1 骨架约束 / L2 静态断言 / L3 实跑用例 / L4 可观测）、5 个实跑用例的断言与证据、12 项静态断言清单、失败类型与拦截层映射，以及已知限制（10 分钟租约与长任务的张力等）。
