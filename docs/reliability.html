AutomationKit 可靠性保障

怎样让生成出来的工作流真正跑得稳 · 四层防线 · 5 个实跑用例 · 12 项静态断言
版本 0.1.0 ｜ 2026-11-01 ｜ 目标运行时 n8n 2.45.0 + Postgres 17 ｜ 与《系统设计文档》配套

为什么单独讲可靠性

这份文档不描述功能，只回答一个问题：工作流写出来之后，凭什么说它能一直跑对。

背景变化很直接：AI 已经能在几分钟内生成一张看起来完整的流程图，成本趋近于零。但生成不等于可用——生成器给出的是「节点连上了」，不是「失败时你知道，重复时不会写两条」。

本项目的 6 个模板全部手写 JSON，依然在一次真实运行中暴露出 6 个缺陷，且全部属于静默失效。这不是生成工具的毛病，而是工作流这类系统的固有属性：它的错误在第一次跑之前不可见。

本轮实跑暴露的缺陷性质读代码能否发现
SQL 返回 0 行时链路并未停止（节点输出 {"success":true}）平台行为与直觉相反不能
ON CONFLICT DO NOTHING 让失败的 key 永久占死设计假设错误不能
占位节点吞掉 payload，下游字段全变 undefined数据流隐式覆盖不能
错误 item 没有 node 字段，落表节点名恒为 unknown平台数据结构不能
日报取数读错来源，静默输出 undefined表达式引用错误不能
Slack 频道占位符不过正则，整条流被判 has issues参数校验可能

结论：可靠性无法靠"写得更仔细"获得，只能靠分层拦截 + 可重复验证。下文四层防线，就是把这 6 类问题分别压到最低成本的那一层去拦。

四层防线

从"生成"到"客户环境运行"，有四个可以加检查的位置。越靠前成本越低，但覆盖面越窄；越靠后覆盖越全，但代价是客户现场才发现问题。

L1

骨架约束 skeleton constraint

不自由生成整张图，只允许在固定骨架里填业务节点。形状不对一眼可见。

拦住

漏错误分支、漏幂等、payload 被覆盖

静态断言 static assertion

不启动 n8n 也能查的机械检查：JSON 结构、节点存在性、占位符格式、版本区间。

拦住

占位符非法、typeVersion 越界、残留凭证与演示节点

▼
L3

实跑用例 runtime cases

导入真实实例，按 5 个固定用例跑一遍，断言数据库状态与执行结果。

拦住

0 行不停链路、失败 key 占死、取数错源、链路断开

▼
L4

可观测 observability

上线后每次失败都落 workflow_errors，四个字段齐全，客户自己能查。

兜住

你预想不到的客户环境特有故障

重心应往前压：L1 + L2 是分钟级、可重复、零成本的；L4 只能告诉你"已经坏了"。把本该 L1 解决的事情留给 L4 兜底，等于把成本转嫁给客户。

模板固定骨架

L1 的具体形状。6 个模板共用同一套骨架，只有中间的"业务节点"不同，因此任何缺件都能被肉眼发现。

[触发] ─▶ [归一化] ─▶ [Claim 占位] ─▶ [Claimed? 闸门] ─▶ [业务节点…] ─▶ [Mark Done 落章]
                        │                  │                 │
                        │(error)           │                 │(error)
                        └──────────────────┴─────────────────┴──────▶ [Log Error]
                                                                          │
                                                                          ▼
                                                                  workflow_errors
                                                     (workflow / node / message / payload)

三个出口的分工

出口触发条件处理方式对客户的可见性
Claim 错误分支数据库不可用 / 权限不足写入 workflow_errors可见，事件不丢
Claimed? 空输出事件已处理过，或仍在租约内静默停止，不写错误表不可见——这正是"去重成功"的表现
业务节点错误分支第三方 5xx、超时、鉴权失败写入 workflow_errors，key 停在 claimed可见，10 分钟后自动可重试

为什么闸门必须单独存在：n8n 2.45.0 的 Postgres 节点在 SQL 返回 0 行时，输出是一条 {"success": true}，不是空输出。所以"0 行 → 后续节点没有输入 → 链路自然停止"这个说法不成立，必须用 Code 节点显式过滤。闸门同时承担另一个职责：把 RETURNING key, payload 带回的 payload 还原成下游可读的字段。

5 个实跑用例

不需要为每个模板设计复杂测试。下面 5 个用例覆盖了本轮暴露的全部缺陷，缺一条就等于没验。

#用例断言本机结果
1 正常输入 业务成功，processed_keys.status = done 通过
2 同一输入连投两次 第二次在闸门停下（lastNodeExecuted = Claimed?），业务侧没有第二条记录 通过
3 外部调用失败（坏域名 / 坏凭证） workflow_errors 多一行，且 node 是真实失败节点名 通过
4 失败后立刻重跑 被 10 分钟租约挡住，不产生重复处理 通过
5 租约回拨 11 分钟后重跑 重新认领成功，并再次落 done 通过

实测证据（2026-11-01，本机实例）

-- 用例 3 落表的真实记录
select id, workflow, node, left(message, 45)
from workflow_errors order by id;
   4 | AutomationKit - Lead Routing | Push to CRM | getaddrinfo ENOTFOUND your_crm_domain

-- 用例 1 / 4 / 5 的状态变化
select key, status, updated_at from processed_keys order by key;
   webhook@example.com::website | claimed | 2026-11-01 11:37:02.626593+08   -- 用例 3 失败后停留
   demo@example.com::cli        | claimed | 2026-11-01 10:40:25.286851+08   -- 用例 4 被租约挡住

补充：真实 Webhook 入口也已验证 —— POST /webhook/lead-routing 返回 200 {"message":"Workflow was started"}，执行记录 mode = webhook、status = success；同一 body 连投两次，错误表不增加。

失败类型与拦截层

用来判断"这个问题该在哪一层解决"。同一类问题放在错误的层，成本会差一个数量级。

失败类型应该被谁拦住成本漏掉的后果
占位符合法性 / typeVersion 越界L2 静态断言最低客户导入即红，或直接无法激活
漏错误分支 / 漏幂等 / payload 被覆盖L1 骨架 + L2 断言低重复写入、失败静默
0 行不停链路 / 取数错源L3 实跑用例中报表含错数、业务侧重复执行
第三方限流 / 网络抖动L3 用例 3 + 运行时重试中偶发丢事件，且无记录
客户环境特有配置（凭证、域名、频道）L4 可观测 + 说明书高只能靠客户自己发现——必须留痕

12 项静态断言

不启动 n8n、不连数据库，纯读 workflow.json 就能查的机械检查。6 个模板全部通过。

#检查项判定依据
1JSON 可解析JSON.parse 不抛错
2存在占位节点节点 query 含 INSERT INTO processed_keys
3占位使用租约query 含 interval '10 minutes' 与 status 判断
4占位有错误分支onError === 'continueErrorOutput'
5占位带回 payloadquery 含 RETURNING key, payload
6存在闸门节点节点名 Claimed?
7闸门还原 payloadjsCode 含 claimKey 且对 payload 做合并
8存在落章节点且接线节点名 Mark Done，且被某节点成功输出指向
9错误落表用真实节点名queryReplacement 含 $prevNode.name
10无残留凭证任何节点不含 credentials 字段
11无演示节点节点名不含 demo（本地调试副本不入交付包）
12坐标紧凑position 为单行数组，便于 diff 与人工复核

为什么第 10、11 项必须有：本地为了跑通会挂演示凭证、加手动触发器。这些一旦混进交付包，客户拿到的是"别人的环境配置"，既跑不了也有安全隐患。断言比"记得删"可靠。

运行时可观测

一次失败必须留下的四个字段

字段来源缺失时你会失去什么
workflow$workflow.name不知道哪个模板出的问题
node$prevNode.name不知道从哪个环节修（写 $json.node.name 会恒为 unknown）
message$json.error.message不知道是鉴权、超时还是字段缺失
payloadJSON.stringify($json)无法重放，只能等客户再发一次

客户自查命令

docker compose exec -T postgres psql -U autokit -d autokit -c \
  "select workflow, node, message, created_at from workflow_errors
   order by created_at desc limit 20;"

日报口径

每日简报统计的是"过去 24 小时"的四个数字，口径固定：processed_keys 的处理量、错误量、复核队列积压量。数字必须从统计查询节点读取，不能从链路上游的占位行读取——这一条曾经写错，导致日报长期输出 undefined。

静默失效是最贵的故障：客户不会因为一次报错来投诉，但会因为"连续两周没收到日报"而流失。因此宁可多写一行错误，也不允许出现"什么都没发生"的假象。

边界与已知限制

限制现状触发条件 / 应对
10 分钟租约是常量写死在 SQL 中，不可配置单次执行超过 10 分钟会出现并发重领。6 个模板均为秒级链路，安全；若接入长任务（大文件、批量 OCR）必须改为可配置或加心跳续租
真实第三方写入未验证Slack / Notion / SMTP / CRM 均为占位地址当前验证的是"失败被正确捕获"，不是"写入成功"。客户配好凭证后需自行跑一次
不保证业务数据一致性业务表由客户定义跨系统的最终一致（eventual consistency）由客户业务侧负责，模板只保证"不重复触发"
agent 类节点有迭代上限当前模板不使用 agent若引入 agent，必须设最大迭代次数，否则一次幻觉可持续烧 token
单实例部署一个 main + 一个 Postgresmain 挂掉期间 Webhook 入口不可用；执行层的高可用（queue mode + worker）属于另一个价格档位
错误表会无限增长无自动清理建议客户按季度归档；量大时按 created_at 分区

可复现的结论：把一个工作流从"能跑"做到"可交付"，靠的不是更聪明的生成，而是骨架约束 + 机械断言 + 固定用例 + 失败留痕这四件事。它们都可以被写成脚本、被别人复核、被下一次复用。
